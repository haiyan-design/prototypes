## 二、文档概述


| 项    | 内容                                                                                                                                                                                        |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 需求编号 | R-261022-019                                                                                                                                                                              |
| 需求名称 | 快速帮用户找到服务                                                                                                                                                                                 |
| 需求背景 | 1. 需要一天 24 小时服务的用户，要下日陪 12h 和夜陪 12h 两单，并且预约两次，理解成本高。 2. 需要连续多天 24 小时服务时，除了拆成日陪、夜陪主单，还要预约多次子单，上门人员也不保证是同一人。 3. 用户进小程序后不容易找到连续陪护。                                                           |
| 需求概述 | 1. 首页放「连陪快约」悬浮球。 2. 用场景、类型、开始日期三个问题，帮用户生成连续多天服务。默认 3 天，可以自己加天数，没有上限。可为自己或他人下单。用户只选一次开始日期，结束时刻由系统算出，钟点不可改。 3. 日间+夜间：全部日班由同一人服务，全部夜班由另一个人服务，共 2 人。用户一笔支付。 4. 从某个具体服务进入时，只把该服务连下多天，不组合日间+夜间。 |
| 业务目标 | 让有连续陪护需求的人群能够快速下单                                                                                                                                                                         |


## 三、整体方案

总体描述（架构图 / 流程图 / 时序图）

```
路径一  连陪快约
首页悬浮球 → 问卷页（服务场景 → 服务类型 → 开始日期）→ 订单页 → 支付

路径二  从服务去下单
某个服务的确认页 → 上门时间只选开始日期 → 支付
```

两条路径算出的班次规则相同。差别是：路径一可以由用户选「仅日间 / 仅夜间 / 日间+夜间」；路径二的商品已经是日间或夜间之一，只连这个班。

支付成功：

- 仅日间或仅夜间，以及路径二：1 笔支付，1 个主单，N 个预约，1 人包完全部天数。
- 日间+夜间：1 笔支付，2 个主单，2N 个预约。日班 1 人，夜班另 1 人。抢单按主单整包，不能拆某一天。

## 五、排班与日期规则

本章把日期和排班的规则收在一起，方便和技术对齐。页面布局、按钮文案仍以第四章为准；两边规则冲突时，以本章为准。

连陪快约、从服务去下单，用的是同一套规则。差别只是：连陪快约可以选择「日间+夜间」；从服务去下单的商品已经是日间或夜间之一。

### 5.1 用户怎么选、系统怎么算

用户只做两件事：选一个**开始日期**，再确认**连续几天**（默认 3 天，最少 3 天，没有上限）。

用户不选结束日期，也不能改钟点。结束时刻、每一天排哪一班，都由系统按「服务类型 + 当前时间 + 开始日 + 天数」算出来。

钟点固定：

- 日班：每天 08:00–20:00
- 夜班：每天 20:00–次日 08:00

已经过了上班时间、但还没到当天截止线时，这一班仍可约，按整班计费。

### 5.2 今天能不能约

截止线 = 默认开始时间再加 3 小时。

| 类型 | 今天还能约吗 | 今天约不了时，最早从哪天起 |
| --- | --- | --- |
| 仅日间 | 现在还没到 11:00 | 明天 08:00 |
| 仅夜间 | 现在还没到 23:00 | 明天 20:00 |
| 日间+夜间 | 日班或夜班只要有一个还能开，今天就可以选 | 两个都过线后，最早明天 08:00 |

日历上，早于最早可约日的日期发灰。点到这些日期，提示「该日期不可约」。

### 5.3 三种类型怎么排

下面的 N 就是用户选的连续天数。

**仅日间**

- 连续 N 个日班
- 开始：开始日 08:00
- 结束：第 N 天的 20:00（也就是开始日往后数 N−1 天那天的 20:00）
- 一个人做完全部日班

**仅夜间**

- 连续 N 个夜班
- 开始：开始日 20:00
- 结束：开始日往后数 N 天那天的 08:00
- 一个人做完全部夜班

**日间+夜间**

- 一定是 N 个日班 + N 个夜班
- 全部日班同一个人，全部夜班另一个人，共 2 人
- 第一班怎么起，看「开始日是不是今天」，以及「今天日班过没过 11:00」：

| 情况 | 从哪一班开始 | 顺序 | 结束 |
| --- | --- | --- | --- |
| 开始日不是今天；或今天日班还没过 11:00 | 开始日的日班 | 日、夜、日、夜… | 开始日往后 N 天那天的 08:00 |
| 开始日就是今天，且已过 11:00、还没过 23:00 | 今天的夜班 | 夜、日、夜、日… | 开始日往后 N 天那天的 20:00 |
| 今天日班、夜班都过线 | 今天选不了 | — | 最早从明天 08:00 的日班起 |

用户加减天数时，开始日不动，只在末尾加一班或删一班。日间+夜间加减时，日班和夜班天数始终一起变。

### 5.4 对照例子

假设现在是 10 月 29 日 20:21（日班已过线，夜班还能约），用户约 3 天：

| 类型 | 开始日 | 开始时刻 | 结束时刻 | 排出来的班 |
| --- | --- | --- | --- | --- |
| 仅日间 | 10/30 | 10/30 08:00 | 11/01 20:00 | 三天日班：30、31、1 日 |
| 仅夜间 | 今天 10/29 | 10/29 20:00 | 11/01 08:00 | 三天夜班：29、30、31 日 |
| 日间+夜间 | 今天 10/29 | 10/29 20:00 | 11/01 20:00 | 六班：夜日夜日夜日 |
| 日间+夜间 | 10/30 | 10/30 08:00 | 11/02 08:00 | 六班：日夜日夜日夜 |

### 5.5 两条入口的差别

| | 连陪快约 | 从服务去下单 |
| --- | --- | --- |
| 类型怎么来 | 用户在问卷里选：仅日间 / 仅夜间 / 日间+夜间 | 进哪个服务就是哪个班，没有日间+夜间 |
| 选日期前 | 必须先选好服务场景和服务类型，否则点日期不生效 | 不用先选题，直接选上门时间 |
| 还没选开始日时 | 问卷里不出现天数和排班 | 上门时间保留标题、「每日 xx:00 上门 · 同一人服务」、最早可约提示和「选日期」；不出现天数；不写「请选择开始日期」 |
| 选中开始日后 | 默认 3 天；问卷里的排班直接展开 | 默认 3 天；出现天数加减；排班默认收起，点「查看排班」再看 |
| 订单页日期 | 叫「服务日期」，按钮是「修改日期」 | 组件相同，叫「上门时间」；没选时是「选日期」，选完收起后是「修改日期」 |
| 连陪提醒 | 问卷页有，随类型变；订单页没有 | 没有 |
| 最早可约那行字 | 问卷页有，选中开始日后收起 | 上门时间标题下有，选中开始日后仍保留 |

换了服务类型，或从服务去下单换了商品：如果原来的开始日对新规则来说已经约不了，清空开始日，并提示「最早可约日已变化，请重新选择开始日期」。

### 5.6 付完款变成什么单

| 类型 | 支付 | 主单 | 预约次数 | 上门人员 |
| --- | --- | --- | --- | --- |
| 仅日间、仅夜间、从服务去下单 | 付 1 次 | 1 个主单 | N 次 | 同一个人做完 |
| 日间+夜间 | 付 1 次 | 2 个主单（日、夜各一） | 2N 次 | 日班一人，夜班另一人 |

抢单按主单整包接，不能拆成某一天单独抢。

钱怎么加：各班（单价 + 等级加价）× 天数，再加 1 次上门费 45。一笔支付只收一次上门费。

### 5.7 提示语

| 什么时候 | 提示什么 |
| --- | --- |
| 问卷里场景、类型都没选就点日期 | 请先选择服务场景和服务类型 |
| 只选了类型，没选场景 | 请先选择服务场景 |
| 只选了场景，没选类型 | 请先选择服务类型 |
| 点到发灰的日期 | 该日期不可约 |
| 天数已经是 3，还要点减少 | 连续陪护至少3天，无法再减少（屏幕正中） |
| 天数加减成功 | 已延长至 {结束时刻} / 已缩短至 {结束时刻}（屏幕正中） |
| 还没选开始日就想收起日历 | 请先选择开始日期 |
| 从服务去下单没选日期就支付 | 请先选择上门时间（至少3天），并打开日历 |
| 没勾协议就支付 | 请先勾选平台服务协议 |
| 问卷三项没齐 | 「下一步」不可点 |

### 5.8 不要做成这样

1. 不要让用户像订酒店一样先选开始、再选结束。
2. 不要在用户只点了一天时，自动帮他延成 3 天区间。
3. 结束时刻和每一班，都必须由开始日、天数、类型和当前时间算出来，不要另开一套选结束日的逻辑。
4. 两条入口的可约规则、排班结果要一致；从服务去下单只是没有「日间+夜间」这一项。
5. 价格以业务最终配置为准。原型里居家日间：从服务去下单是 ¥335，连陪快约确认页是 ¥360；护士日间暂按 ¥800。
